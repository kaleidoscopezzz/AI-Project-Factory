# 需求拆解与 Goal 规划

把需求变成有边界、有顺序、可验证的计划。方法是“功能拆解 → Goal 划分 → 逐阶段开发 → 验收 → 冻结”，不携带任何特定行业的固定业务模块。

## 输入与缺口
接收任一种需求载体，附带工作目录、已有状态、目标用户、部署场景、技术限制及操作权限（若已提供）。先读取用户指定的需求和现有 PROJECT_STATUS / AGENTS；已有工程只做必要的局部检查。为每项结论标注“用户明确 / 仓库事实 / 可撤销假设 / 待确认”，需求来源注明文件与章节或本次输入。

一句话输入也要给出可用草案。可以暂定可撤销的工程细节并说明；涉及业务规则、真实身份和数据、外部系统、生产部署、费用、重大权限或交付范围的缺口列为阻塞项。继续不依赖答案的规划；不得把无答复当批准。既有项目先做增量影响评估，不以 Goal 0 名义重建已冻结基座。

## 工作流程
1. 确定项目定位、用户、业务结果、范围内/外内容及成功指标。区分 DEMO、内部真实系统、公开服务、移动/桌面/CLI 工具；描述实测平台和目标平台的区别。
2. 逐条提取需求，赋予稳定 R-ID。按用户任务闭环拆模块、功能点和状态转换，覆盖正常、异常、权限、取消、刷新/重启与关联一致性。将非功能要求（运行环境、可用性、性能、离线、审计等）同样编号；无依据的数值不可伪装成用户要求。
3. 每个功能点绑定 AC-ID，写出前置条件、用户/API 动作、可观察结果、验证方法。例：重复提交同一幂等键只生成一个记录，而非“支持幂等”。复杂功能可有多个 AC，简单点也不能只写“界面正常”。标明哪些 AC 是设计建议、需确认后生效。
4. 划分阶段：Goal 0 建可运行的最小工程基础和纵向样板；Goal 1 起交付完整业务闭环。每阶段记录进入基线、产物、验收、冻结边界、后续扩展入口；业务范围不得塞入基础建设以提前实现。Release 另设阶段，仅在交付形态需要时安排。
5. 建有向无环依赖和顺序。为未来 Agent 列 Task-ID、角色、输入、输出、可写范围、独占共享文件、依赖和 AC。检查每个步骤所需的文件/契约已由前置任务提供，或该任务有权限创建，不能要求先迁移/初始化却把模型定义交给后置任务。仅共享契约稳定、写集不重叠的任务可并行；根配置、锁文件、路由装配、迁移注册和状态文件交给单一整合者。
6. 列出重大歧义、选择及影响、阻塞的任务、推荐但尚未获准的方向；列风险、限制、禁止擅自实现的功能。把新增“建议功能”放候选，不计入承诺范围。
7. 用 [计划模板](assets/requirement-plan.md) 输出计划；需要处理招标条款、复杂阶段或并行划分时读 [拆解检查](references/decomposition.md)。输出应能作为 goal0-scaffolder 或 goal-prompt-writer 的输入，也可直接交给人工 Coder。

## 输出与质量门槛
输出一份需求计划 Markdown，覆盖定位边界、模块功能点、Goal 0/1/2…、逐点验收、依赖与顺序、并行候选、待确认、风险/禁止项。附需求→AC→Goal→Task 的映射，不必另建重复文件。若消费者要求机器任务包，依据已确认的映射输出稳定 ID，不生成调度程序。

检查：所有范围内需求均有阶段和可观察 AC；每个 Task 有责任人及写集；依赖无环；Goal 0 可独立运行但未冒充业务完工；未知项不写成事实；无参考行业内容污染；计划自测与外部验收分开。发现矛盾时标记阻塞并说明受影响范围，保留其余可用草案。

## 使用示例
“使用 $requirement-planner：为单机断网演示的采购申请系统拆分需求。暂不接支付和电子签章，生成阶段计划与逐项验收。”应输出采购任务闭环和离线限制，而不是政法模块。

“使用 $requirement-planner：现有企业库存系统增加调拨审批。读取现有状态，输出增量 Goal 与兼容回归要求。”应复用已验收基础，指出调拨事务及权限歧义，不重新建库。
