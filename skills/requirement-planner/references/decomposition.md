# 复杂需求拆解检查

## 需求载体
- 招标：逐条保留条款编号、必选/可选、证明方式；“演示功能”与“真实对接”分别列；无法获取附件时标缺失，不猜条款。
- PRD：角色→业务对象→动作→状态→数据影响→异常；检测不同章节冲突。
- 一句话：先界定用户/价值和一个最小闭环，再补确认清单；不能默认行业法规、组织层级、审批人数。
- 现有项目：先核对当前阶段、已验收契约、局部数据模型；新增需求给独立增量 Goal，列既有流程回归。

## 阶段选择
Goal 0 的登录、权限和持久化只建到后续业务可接入的深度。真实系统须具备最小服务端授权和数据库纵向链路；DEMO 应明确模拟身份边界。无 UI 工具以 CLI/协议和运行证据代替截图，不能为了模板强造菜单。

按依赖和可验收的闭环划阶段，不按文件数量或模块名称机械拆。采购申请→审批→执行可分阶段；后一步依赖前一步契约。真实库存扣减与重复请求保护应在同一闭环验收，不能拆成一个“看起来完成”的按钮阶段。

## 验收反例与修正
- “权限完善”→用户甲直接请求用户乙资源：返回 403/404，数据库无变更，审计不暴露敏感字段。
- “刷新正常”→记录变更后刷新/重启，ID 与已提交状态保留，指标由同一记录计算。
- “可取消”→确认对话框取消后，记录、日志和统计均不变。
- “支持恢复”→处理中重启后恢复同一操作标识或进入明确失败状态，不生成第二份业务记录。

## 并行检查
对任务写集求交集。交集含配置、锁文件、共享类型、数据库迁移、导航或状态文档时先拆出单一整合任务。只读分析可以并行；Tester 与 Reviewer 可在同一固定候选版本上独立只读检查，但修复开始后旧结论需要重新关联新候选版本。
