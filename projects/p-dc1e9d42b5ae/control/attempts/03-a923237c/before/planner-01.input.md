# 需求拆解与 Goal 规划

把需求变成有边界、有顺序、可验证的计划。方法是“功能拆解 → Goal 划分 → 逐阶段开发 → 验收 → 冻结”，不携带任何特定行业的固定业务模块。

## 输入与缺口
接收任一种需求载体，附带工作目录、已有状态、目标用户、部署场景、技术限制及操作权限（若已提供）。先读取用户指定的需求和现有 PROJECT_STATUS / AGENTS；已有工程只做必要的局部检查。为每项结论标注“用户明确 / 仓库事实 / 可撤销假设 / 待确认”，需求来源注明文件与章节或本次输入。

一句话输入也要给出可用草案。可以暂定可撤销的工程细节并说明；涉及业务规则、真实身份和数据、外部系统、生产部署、费用、重大权限或交付范围的缺口列为阻塞项。继续不依赖答案的规划；不得把无答复当批准。既有项目先做增量影响评估，不以 Goal 0 名义重建已冻结基座。

## 工作流程
1. 确定项目定位、用户、业务结果、范围内/外内容及成功指标。区分 DEMO、内部真实系统、公开服务、移动/桌面/CLI 工具；描述实测平台和目标平台的区别。
2. 逐条提取需求，赋予稳定 R-ID。按用户任务闭环拆模块、功能点和状态转换，覆盖正常、异常、权限、取消、刷新/重启与关联一致性。将非功能要求（运行环境、可用性、性能、离线、审计等）同样编号；无依据的数值不可伪装成用户要求。
3. 每个功能点绑定 AC-ID，写出前置条件、用户/API 动作、可观察结果、验证方法。例：重复提交同一幂等键只生成一个记录，而非“支持幂等”。复杂功能可有多个 AC，简单点也不能只写“界面正常”。标明哪些 AC 是设计建议、需确认后生效。
4. 划分阶段：Goal 0 建可运行的最小工程基础和纵向样板；Goal 1 起交付完整业务闭环。每阶段记录进入基线、产物、验收、冻结边界、后续扩展入口；业务范围不得塞入基础建设以提前实现。Release 另设阶段，仅在交付形态需要时安排。
5. 建有向无环依赖和顺序。为未来 Agent 列 Task-ID、角色、输入、输出、可写范围、独占共享文件、依赖和 AC。检查每个步骤所需的文件/契约已由前置任务提供，或该任务有权限创建，不能要求先迁移/初始化却把模型定义交给后置任务。仅共享契约稳定、写集不重叠的任务可并行；根配置、锁文件、路由装配、迁移注册和状态文件交给单一整合者。
6. 列出重大歧义、选择及影响、阻塞的任务、推荐但尚未获准的方向；列风险、限制、禁止擅自实现的功能。把新增“建议功能”放候选，不计入承诺范围。
7. 用 [计划模板](assets/requirement-plan.md) 输出计划；需要处理招标条款、复杂阶段或并行划分时读 [拆解检查](references/decomposition.md)。输出应能作为 goal0-scaffolder 或 goal-prompt-writer 的输入，也可直接交给人工 Coder。

## 输出与质量门槛
输出一份需求计划 Markdown，覆盖定位边界、模块功能点、Goal 0/1/2…、逐点验收、依赖与顺序、并行候选、待确认、风险/禁止项。附需求→AC→Goal→Task 的映射，不必另建重复文件。若消费者要求机器任务包，依据已确认的映射输出稳定 ID，不生成调度程序。

检查：所有范围内需求均有阶段和可观察 AC；每个 Task 有责任人及写集；依赖无环；Goal 0 可独立运行但未冒充业务完工；未知项不写成事实；无参考行业内容污染；计划自测与外部验收分开。发现矛盾时标记阻塞并说明受影响范围，保留其余可用草案。

# 复杂需求拆解检查

## 需求载体
- 招标：逐条保留条款编号、必选/可选、证明方式；“演示功能”与“真实对接”分别列；无法获取附件时标缺失，不猜条款。
- PRD：角色→业务对象→动作→状态→数据影响→异常；检测不同章节冲突。
- 一句话：先界定用户/价值和一个最小闭环，再补确认清单；不能默认行业法规、组织层级、审批人数。
- 现有项目：先核对当前阶段、已验收契约、局部数据模型；新增需求给独立增量 Goal，列既有流程回归。

## 阶段选择
Goal 0 的登录、权限和持久化只建到后续业务可接入的深度。真实系统须具备最小服务端授权和数据库纵向链路；DEMO 应明确模拟身份边界。无 UI 工具以 CLI/协议和运行证据代替截图，不能为了模板强造菜单。

按依赖和可验收的闭环划阶段，不按文件数量或模块名称机械拆。采购申请→审批→执行可分阶段；后一步依赖前一步契约。真实库存扣减与重复请求保护应在同一闭环验收，不能拆成一个“看起来完成”的按钮阶段。

## 验收反例与修正
- “权限完善”→用户甲直接请求用户乙资源：返回 403/404，数据库无变更，审计不暴露敏感字段。
- “刷新正常”→记录变更后刷新/重启，ID 与已提交状态保留，指标由同一记录计算。
- “可取消”→确认对话框取消后，记录、日志和统计均不变。
- “支持恢复”→处理中重启后恢复同一操作标识或进入明确失败状态，不生成第二份业务记录。

## 并行检查
对任务写集求交集。交集含配置、锁文件、共享类型、数据库迁移、导航或状态文档时先拆出单一整合任务。只读分析可以并行；Tester 与 Reviewer 可在同一固定候选版本上独立只读检查，但修复开始后旧结论需要重新关联新候选版本。

# 架构选择与基础门槛

## 按部署和真实性决策
| 场景 | 可行方案 | 选择依据 | 不可偷换 |
| --- | --- | --- | --- |
| 离线演示 Web | 静态 SPA + 确定性数据 + 本地资源；需要附件/大数据可选本地服务+SQLite | 展示目标、目标设备、存储容量、交付启动方式 | 演示账号不等于真实认证；离线不等于离线安装开发工具 |
| 多人真实企业 Web | UI + 服务端 API + 关系数据库；按团队能力选单体/分层 | 事务、并发、资源授权、审计、维护成本 | 不把浏览器缓存当权威存储；禁止服务不可用时转 Mock 成功 |
| 桌面/移动 | 原生或跨平台 UI + 本地/远程存储 | 设备 API、平台分发、同步与离线需求 | 不强制 Web 菜单或 Windows 便携包 |
| CLI/后台服务 | 命令或 API、结构化日志、单元/集成测试 | 无 UI、协议、部署与运维 | 截图可不适用，但输出、退出码、健康/日志证据不可省略 |

不要由行业名称推导技术栈。选择一个够用的方案；未要求微服务、消息队列、付费云或 AI API 时不主动引入。

## 基础纵向样板
最少串通入口→输入验证→动作→存储/事务→读取→错误→证据。可选虚构“基础样例记录”，不提前实现采购审批或库存出入库。样板入口标“工程验证”，后续移除/保留策略明示。先冻结接口，再交给业务增量开发。

## 状态不变量
- 模板不可变、运行状态独立；列表/详情/指标/审计同源。
- 对取消动作无写入；异步返回必须核对操作版本/取消标志，不能覆盖重置后新状态。
- 正在执行需要明确可见的开始和终态，不预置永久运行记录以假装功能。
- 模拟时钟只在演示需求成立时采用；真实项目使用明确服务端时区/时间语义。
- DB 迁移和 seed 幂等，真实系统的破坏性 reset 限隔离开发测试库并校验环境；不得擦掉用户数据以修测试。

## 验证取舍
每个重要不变量至少一个可失败的验证：未经授权的直接 API 请求、重复提交、刷新/进程重启、取消无变化、存储失败、迁移幂等。无需为纯文本或目录创建镜像测试。UI 用 Playwright 或平台对应框架；后端按语言用原生测试框架和真实隔离 DB，不能只 Mock 掉数据库。

断网 DEMO 应阻断外部域名但允许本地服务。真实企业项目记录已声明 API/DB 请求，预期的业务拒绝可列白名单；意外错误必须归零或获得明确豁免。不统一要求所有 HTTP 请求都 200。

交付可先有开发运行说明，真正便携打包或生产发布由后续阶段验收。正式包从固定候选源码构建，记录版本/哈希/依赖和目标设备实测；未测平台如实列限制。

# 可直接执行的 Goal 开发提示词

目标是让 Coder 不必猜任务范围或完成条件。详细、精确、步骤可执行；复杂度决定长度，约束不能因压缩消失。本 Skill 写提示词，不自动启动 Coder、提交或发布。

## 输入和输出
输入项目背景、目标目录/环境、需求计划/AC、当前 Goal/Git 基线、工程方案、冻结/可写边界、用户操作授权、验收反馈（如有）。独立使用也可：把输入中的明确需求转换成最小 AC，不强制其他 Skills 已安装。
输出一份可直接复制的 Coder 提示词；必须有具体动作、期望结果、验证入口和停止规则。可附一份交接信息表（Task-ID、输入版本/指纹、depends_on、write_set、AC-ID、命令、证据、approval、retry_budget）；这只是接口设计，不宣称调度器已实现。

## 编写步骤
1. 先对输入作一致性检查：目标目录是否存在、基线是否实测、已确认/假设/阻塞是否分清、当前权限是否支持任务。只读检查实际可获得的信息；未知 HEAD 写“实现前只读核验”，新目录写“无仓库/无基线”，不得捏造 Commit、测试通过或版本号。
2. 选择完整 Goal、增量功能、定向修复或发行任务模式。完整 Goal 使用 [Goal 提示词模板](assets/goal-development-prompt.md)，定向任务可合并章节，但保留目录/基线、范围、实施、AC、允许/禁止、测试证据、失败/停止和报告。
3. 把功能写成编号操作。每步说明修改入口、依赖/前置、页面或 API 行为、数据影响、错误/取消/禁用、AC 与验证。核对执行该步所需产物已经存在或可在其写集内创建，不能只有无环依赖而实际顺序不可执行。复杂异步写明开始、锁定、终态、刷新/重启恢复和旧结果取消；统计和列表不得各造数据。
4. 写实际 UI/交互和数据/状态要求；无 UI、无数据库或无需截图的任务明确不适用及替代证据，不为凑模板引入功能。DEMO 和真实实现边界单独说明；既有冻结代码只允许任务要求的兼容扩展，禁止整体重构。
5. 明确路径级允许修改、禁止修改和操作权限。依赖升级、全局配置、外部服务、Git 写入、部署/发布分别看现有授权；提示词不能授予输入没有的权限。本次禁 Git 的限制不自动传播为其他项目永禁 Git；未来提交冻结仍需明确控制点。
6. 给命令或明确的运行接口：工作目录、工具/环境前提、实现时应创建的脚本、执行顺序、成功退出码、测试对象、证据路径。区别拟定命令与实测命令；不要输出一个不存在的脚本并暗示它已可运行。已选技术栈使用自身工具，不能所有项目一律 pnpm/Playwright。
7. 用 [精确写作与异常规则](references/writing-guide.md) 检查每条 AC：正常、异常、权限/边界、取消无副作用、状态关联、兼容/恢复至少覆盖实际相关项。测试不能只验证按钮出现；不能用直接 store 操作替代用户链路，也不能禁用失败断言换绿灯。
8. 定义证据与报告。证据绑定候选基线及工作区内容指纹、步骤、环境、实际结果、日志/截图路径；UI 有多个目标视口时按实际要求检查。报告按模板列变更、AC、命令、证据、受保护范围、Git、风险和状态。需要状态/验收产物时使用 [状态模板](assets/project-status.md) 和 [验收模板](assets/acceptance-record.md)。
9. 写有限返工与停止条件：默认同一问题最多 2 次有针对性的修复，整体最多 3 轮验证；用户已有预算优先。每次保留失败信息、说明修复原因；未知环境问题不无限安装、换栈或扩大范围。遇需求阻塞、授权不足、越界、数据破坏风险或达到预算时停止依赖任务，报告可继续部分，不把测试失败标完成。
10. 明确完成后停在“已完成，待外部 Reviewer 验收”。不进入下一 Goal，不自动冻结，不把自测当外部通过。单个 Coder 应能独立完成实施与自测，不能依赖尚未提供的多 Agent 调度器；独立 Review 另由有授权的审查者进行，Coder 自检不得冒充独立结论。删掉最终提示词中未替换的模板占位符；若关键决策仍阻塞，输出标为“草案，不可派发”，列问题而不是伪装成最终命令。

## 完稿门槛
完整任务的 16 项有内容或合理不适用：背景、目录、环境栈、Git/Goal 基线、目标、功能步骤、页面交互、数据状态、允许修改、禁止修改、测试运行、截图证据、完成标准、失败处理、报告、完成后停止。每个关键 AC 能定位到步骤和测试；环境无法证实的不写已通过；权限继承不扩大；复杂任务可独立复制执行，无须读聊天历史。

## 使用示例
“使用 $goal-prompt-writer，根据采购 DEMO 计划和 Goal 0 方案生成 Coder 提示词；禁止 Git 写操作，完成后待验收。”应指定可运行基座、断网验证、模拟边界和重置隔离。
简单修复也要明确：“在已核验基线中修正弹窗取消后仍写入的问题；只改相关动作与必要回归；点击取消后记录、审计和指标均不变；运行该链路和原确认回归并留证；失败两次停止；报告变更、证据、Git与限制；待外部验收后停止。”最终稿还须填真实目录、基线和项目命令。

# 精确提示词写作与异常规则

## 风格来源和适用范围
这种写法从一个已验收项目的工程结果、阶段记录和用户详细指令归纳。它不是任何历史对话提示词的原文。可复用的是边界、顺序、状态不变量、证据和停止规则；具体行业、主题、版本、测试数量、分辨率不得当作所有项目要求。

## 从建议到指令
- “做好基础工程”→“在指定目录创建配置、运行脚本、布局和一个持久化样板；用生产构建启动，点击修改、刷新读取并核对同一 ID。”
- “按钮有交互”→“取消不变；确认提交期间禁用重复提交；失败留原记录并给可读错误；成功同步列表/详情/指标/日志。”
- “权限正确”→“角色甲直接调用禁止动作返回 403，数据库无变更；UI隐藏/禁用有提示；服务端结果是授权依据。”
- “截图正常”→“在指定实际 viewport 采集未裁剪 PNG，附页面、步骤、候选版本；检查标题、操作入口和弹窗可达。”

写“做什么→为何需要→如何观察”。固定样例 ID、预期数值只在可控 seed 中采用；真实数据指标用计算口径和断言关系，不能硬编码图表。

## 三种模式
完整 Goal：全部必要条目与执行表。增量/修复：带触发→原行为→目标行为、最小改动路径、冻结兼容回归。Release：指定已确认候选源码、构建来源、包内外版本、哈希及独立解压 smoke，外部发布须已有授权；不能用旧 ZIP 换名字冒充新构建。

简单任务可一段或几段，但仍要真实目录/基线、修改边界、动作/结果、验证、有限重试、报告和待验收停止。不要把所有大型框架要求搬到文案修复。

## 异常和预算
同一问题两次有针对性修复仍失败就停止该链路；全任务三轮验证达限，保留可审查结果并报告阻塞。测试失败不得无限重试碰运气；基础环境缺失先诊断，不反复安装或擅自换栈。超预算、需求冲突、授权缺失、越界、真实数据破坏、未知进程占用均按具体影响停相应动作，不强杀、不覆盖。

已经授权的修复可在边界内继续，无需每改一文件问用户；重大业务歧义或新增外部副作用才等待决定。待验收阶段不自动继续下一 Goal。

## 可派发检查
没有模板占位符；所有关键输入可随提示词或明示路径获得；不存在互相冲突的“必须改/禁止改”；命令输入输出和前置清楚；AC有对应行为验证；冻结边界、证据和最终报告明确。存在阻塞则写“草案，不可派发”，单列可继续的任务，不制造完整可执行的假象。
